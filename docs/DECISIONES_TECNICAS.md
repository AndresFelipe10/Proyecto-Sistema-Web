# Decisiones Técnicas (ADR resumido)

Cada entrada documenta una decisión fundamental y su motivo. Nuevas decisiones relevantes se agregan aquí, nunca se cambian silenciosamente en el código.

| Decisión | Alternativa descartada | Motivo |
|---|---|---|
| Laravel 12 | PHP puro | Productividad, ecosistema maduro (Eloquent, Policies, testing), estándar de facto para este tipo de proyecto académico-profesional |
| Docker Compose | XAMPP | Reproducibilidad, paridad dev/producción, el cliente final no instala nada |
| Blade + Bootstrap 5 | React/Vue/Angular | El alcance no requiere SPA; menor complejidad, curva de aprendizaje y superficie de mantenimiento para el equipo actual |
| MySQL 8+ | PostgreSQL, SQLite | Estándar en hosting de bajo costo típico de pequeños emprendimientos; suficiente para el volumen de datos esperado |
| Multi-tenancy lógico (`business_id`) | Bases de datos separadas por tenant / schemas separados | Menor complejidad operativa y de costos para el volumen esperado de pequeños emprendimientos; el aislamiento se garantiza con Global Scope + Middleware + Policies |
| Módulo IA desacoplado (`AiProviderInterface`) | Acoplar directamente al SDK de Gemini | Permite sustituir de proveedor sin reescribir el núcleo; evita que la IA se convierta en dependencia crítica |
| Gemini como proveedor inicial | OpenAI, Claude, modelo local | Nivel gratuito disponible para etapa académica; decisión revisable, por eso la abstracción |
| IA en modo solo lectura | Permitir escritura vía IA desde el inicio | Reduce drásticamente la superficie de riesgo (alucinaciones, prompt injection) en la primera versión |
| Sin Redis/colas en el MVP | Procesamiento asíncrono de IA | La llamada síncrona con timeout corto es suficiente para el volumen esperado; se evita complejidad operativa innecesaria. Reevaluar solo si el tiempo de respuesta se vuelve un problema real medido en producción |
| Sin phpMyAdmin en el compose por defecto | Incluirlo siempre | No es necesario para el funcionamiento del sistema; puede agregarse como `docker-compose.override.yml` opcional si se requiere durante desarrollo |
| Docker Compose inmutable en producción | Montar código fuente con bind mounts en prod | Garantiza inmutabilidad, consistencia entre réplicas, máximo rendimiento con OPcache precompilado y seguridad al no exponer el sistema de archivos del host |
| Scripts operativos en Bash nativo | Ansible, Terraform o herramientas pesadas de CI/CD | Mantiene la infraestructura simple, autocontenida y comprensible para pequeños emprendimientos o administradores de sistemas en VPS básicos |
| Endurecimiento de seguridad con herramientas nativas de Laravel | Paquetes de terceros de seguridad | Minimiza la superficie de ataque y dependencias externas; Laravel 12 ya provee rate limiting, protección CSRF y sanitización nativa |
| Zona horaria centralizada en `America/Bogota` (UTC-5) a nivel de aplicación | Almacenar en UTC y convertir en cada vista/Blade con `setTimezone()` | Todas las fechas y transacciones son generadas por Carbon/Laravel dentro del contexto exclusivo de negocios de Cali, Colombia; unificar la zona horaria en la aplicación (`config('app.timezone')`) asegura consistencia nativa en formularios POS, reportes, dashboard y base de datos sin requerir conversiones repetitivas en cada plantilla |
| Descuento como porcentaje con columna aditiva `discount_percentage` | Reemplazar la columna `discount` existente; recibir monto en pesos del frontend | Se agrega `discount_percentage DECIMAL(5,2)` con CHECK constraint real en MySQL (0-100) sin modificar `discount`. El backend calcula `discount = subtotal × (pct/100)` — nunca se confía en un valor monetario enviado por el cliente. Ambas columnas coexisten: `discount` para compatibilidad/reportes financieros, `discount_percentage` para trazabilidad histórica del porcentaje real aplicado |
| Comprobantes de venta con impresión nativa del navegador (dos formatos) | Librería de generación de PDF (dompdf, wkhtmltopdf) | Dos vistas Blade dedicadas con CSS `@media print` + `window.print()`: factura (carta/A4) y ticket térmico (80mm). Evita agregar dependencias pesadas; el usuario controla la impresora desde el diálogo nativo del navegador. Ambos formatos protegidos por `SalePolicy::view()` para mantener aislamiento multi-tenant |
| Prioridad de Middleware `SetCurrentTenant` previa a `SubstituteBindings` y defensa en profundidad en Policies | Depender únicamente de Global Scope en controladores sin verificar `business_id` en Policies | Laravel ejecuta `SubstituteBindings` como parte del grupo `web`. Sin priorizar explícitamente `SetCurrentTenant`, la resolución de modelos en rutas se evaluaba antes de activar el tenant, permitiendo fugas cross-tenant vía Route Model Binding. Se corrigió anteponiendo `SetCurrentTenant` a `SubstituteBindings` en la lista de prioridades de `bootstrap/app.php` y agregando verificación obligatoria `$model->business_id !== session('current_business_id')` en todas las Policies de modelos tenant-aware como segunda barrera independiente |
| Bloqueo pesimista y constraint UNIQUE en numeración consecutiva de facturas | Generación optimista de números de factura sin índice único en base de datos | Para prevenir colisiones o números duplicados bajo concurrencia en el POS, se aplica `lockForUpdate()` sobre la última venta dentro de la misma transacción atómica de `processSale` y se añade un índice UNIQUE compuesto `(business_id, invoice_number)` en la tabla `sales` |
| Saneamiento transversal de celdas CSV contra Formula Injection (CWE-1236) | Confiar en que los datos de entrada del usuario están limpios o no contienen fórmulas de hojas de cálculo | Se implementa `sanitizeCsvCell()` anteponiendo un apóstrofe (`'`) a cualquier celda de texto que comience con caracteres ejecutables en Excel/Calc (`=`, `+`, `-`, `@`, `\t`, `\r`), aplicado mediante `array_map` a todas las filas generadas en `ReportService` |
| Transmisión de clave de IA en cabecera HTTP y sanitización de registros de error | Enviar API key como query param en URL (`?key=...`) y loguear `$e->getMessage()` crudo | Las claves en query strings quedan registradas en proxies, balanceadores y trazas de error de HTTP. Se estandariza el uso de la cabecera `x-goog-api-key` y se filtran tokens y URLs en `AiQueryService` antes de escribir en `laravel.log` |
| Protección contra autodegradación del único administrador del tenant | Permitir que cualquier usuario con rol admin modifique roles sin validar cardinalidad mínima | Evita bloqueos irreversibles donde el único administrador activo se degrada a empleado o es degradado sin supervisión. Se añade validación estricta de autorización en `UserController::update` y comprobación de cardinalidad mínima de administradores activos |
| Resolución autoritativa de precio unitario en backend bajo lock pesimista y límite de cantidad | Confiar en `items.*.unit_price` enviado por el cliente o formularlo en el frontend | El precio unitario de cada línea de venta se resuelve SIEMPRE desde `products.sale_price` en backend dentro de la transacción bloqueada (`lockForUpdate`); el valor enviado por el cliente se usa solo como referencia de UI, nunca para el cálculo. Subtotal, descuento y total son 100% derivados en backend. Adicionalmente se acota `items.*.quantity` a un rango razonable (`max:99999`) para prevenir abusos. Motivo: hallazgo `pos-line-item-unit-price-tampering` (Run 2 del security audit) |

> Cualquier decisión que reemplace o contradiga una fila de esta tabla debe agregarse como nueva fila, explicando el motivo del cambio — nunca se borra el historial de decisiones.
